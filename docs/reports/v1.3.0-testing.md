# Markdown Diff Cat 1.3.0 테스트 보고서 — 실제 리뷰 흐름, 화면 모양 5가지, 검증 등급

> 2026-10-09 · 테스트 저장소 [drum-grammer/markdown-diff-cat-testbed](https://github.com/drum-grammer/markdown-diff-cat-testbed)(내용 v2) · 하네스 [testbed/](../../testbed/README.md) · 검증 등급 [README · Verification tiers](../../README.md#verification-tiers) · 앞선 보고서: [1.1.1 테스트 저장소](v1.1.1-testbed.md) · 아직 게시하지 않은 변경: [UNRELEASED](../releases/UNRELEASED.md)
>
> **English summary** — The test repository first had three pull requests, six seeded threads, and fifteen scenarios. It covered no outdated threads, no whole-file comments, no suggestions, and no richly formatted comments, and it ran only in the maintainer's Split layout. Version 2 adds a pull request with a follow-up commit after review and five more seeded threads. It also runs the layout-sensitive scenarios in all five GitHub diff layouts (Split, Unified, Hide whitespace, Minimize comments, Compact line height). The two settings that exist only on the GitHub account are restored after each run. On 1.2.0 this baseline passed 51 of 57: comments on the whole file were invisible in the rendered view, in every layout. 1.3.0 shows them at the top of the file and lets you preview, edit, and delete your own comments. The requests behind these features were taken from GitHub's own Files changed page. The checks are now three tiers: `pnpm verify quick` (43 s, while you work), `pnpm verify pr` (5 min 35 s, before merging), and `pnpm verify release` (15분 29초, before asking for review). Each tier writes a formatted report. All three pass on 1.3.0.

## 1. 테스트 저장소 점검 — 있던 것과 빠진 것

1.1.1 때 만든 하네스는 이미 실제로 코멘트를 쓰고 API로 다시 읽었다. 그래도 실제 리뷰에서 흔한 장면이 빠져 있었다.

| 장면 | 1.1.1 하네스 | 왜 필요한가 |
|---|---|---|
| 리뷰 뒤 작성자가 고친 커밋 → 낡은 스레드 | 없음 | 리뷰를 주고받는 PR은 거의 다 이렇게 된다 |
| 파일 전체에 단 코멘트 | 없음 | "이 문서 전체에…" 같은 코멘트는 줄이 없다 |
| 제안(suggestion) 코멘트 | 없음 | 리뷰어가 고칠 글을 그대로 제안한다 |
| 코드·목록·링크가 든 코멘트 | 없음(글 한 줄만) | 코멘트 본문을 GitHub 모양 그대로 보여 주는지 |
| 보류 중인 리뷰에서 답글 올리기 | 버튼 모양만 봄 | 리뷰를 모아 내는 사람의 흐름 |
| ⌘Enter로 올리기 · 합친 표 행에 올리기 | 없음 · 줄 고르기만 | 키보드 흐름 · 표가 많은 문서 |
| GitHub 화면 모양(톱니바퀴 메뉴) | 본인 설정(Split)에서만 | Unified를 쓰는 사람, 공백 숨김·코멘트 접기를 켠 사람 |
| 내 코멘트 편집·삭제·미리보기 | 기능 없음 | 경쟁 분석 개선 제안 4번 |

## 2. 고친 테스트 — 내용 v2

**새 PR [#7 리뷰 뒤 따라온 커밋](https://github.com/drum-grammer/markdown-diff-cat-testbed/pull/7/changes)** — `docs/roadmap.md`에 첫 커밋을 올리고 리뷰를 단 뒤, 작성자가 한 줄을 다시 고친 커밋을 올린 PR이다. 커밋 시각을 고정해 같은 내용이면 같은 커밋이 되고, 설정은 여러 번 돌려도 결과가 같다. 심은 스레드는 다섯 개다.

| 심은 스레드 | 무엇 |
|---|---|
| `outdated` | 첫 커밋의 12번째 줄 — 다음 커밋이 그 줄을 바꿔 낡는다 |
| `current` | 그대로인 줄(6) |
| `file` | 파일 전체 코멘트(`subject_type: file`) |
| `suggest` | 제안 블록(```` ```suggestion ````) |
| `rich` | 번호 목록·굵게·인라인 코드·링크·코드 블록 |

**화면 모양 5가지** — GitHub "Files changed"의 톱니바퀴 메뉴를 하나씩 바꿔 가며 돈다. 바꾸는 법을 먼저 확인했다(2026-10-09).

| 화면 모양 | 바꾸는 법 | 계정 설정 |
|---|---|---|
| Split | 주소 `?diff=split` | 안 바뀜 |
| Unified | 주소 `?diff=unified` | 안 바뀜 |
| Hide whitespace | 주소 `?w=1` | 안 바뀜 |
| Minimize comments | `POST /users/diffview {"commentsPreference":"collapsed"}` | **바뀜** — 바꾸기 전 값을 적어 두고, 끝나면 되돌린다 |
| Compact line height | `POST /users/diffview {"lineSpacing":"compact"}` | **바뀜** — 같음 |

계정 설정을 바꾸는 두 모양은 바꾸기 전 값을 `.scratch/testbed/layout-original.json`에 적어 둔다. 프로젝트가 끝나면 되돌리고, 중간에 멈춰도 다음 실행이 맨 먼저 되돌린다. 실행 뒤 본인 설정은 그대로였다(Split, 나머지 꺼짐). 모든 시나리오는 Split에서 돌고, 화면 모양에 따라 달라질 수 있는 시나리오(`@layout` 9개)만 나머지 넷에서 다시 돈다.

**새 시나리오 T16–T24**

| | 무엇 | 확인 |
|---|---|---|
| T16 | 파일 전체 코멘트가 파일 맨 위에 보이고 답글을 달 수 있다 | 화면 + REST `in_reply_to_id` |
| T17 | 낡은 스레드는 GitHub처럼 본문에 두지 않고 요약에도 세지 않는다 | 화면 + 요약 "스레드 4개" |
| T18 | 제안·서식 코멘트를 GitHub 모양 그대로 | 제안 표·목록·코드·링크 |
| T19 | 보류 중인 리뷰가 있을 때 답글은 그 리뷰의 보류 중 답글 | GraphQL 상태 PENDING |
| T20 | ⌘Enter(Ctrl+Enter)로 바로 올리기 | REST 범위 26–28 |
| T21 | 합친 표의 바뀐 행에 코멘트 → 그 행의 줄, 다시 열면 표 뒤 | REST + 화면 |
| T22 | 내 코멘트 편집(미리보기 포함) | REST 본문 |
| T23 | 내 코멘트 삭제(두 번 눌러야) | REST에서 사라짐 |
| T24 | 새 코멘트 미리보기(굵게·코드·멘션), 올리지 않고 닫기 | 화면 |

**실패하면 남기는 것** — 시나리오마다 크롬 기록(trace: 화면·DOM·네트워크)을 켜 두고, 실패하면 결과 폴더에 `trace.zip`과 페이지 콘솔을 남긴다. 가끔만 실패하는 것을 다음에 가리기 위해서다(§4).

## 4. 찾은 것과 고친 것 — 1.3.0

| 찾은 것 | 원인 | 1.3.0 |
|---|---|---|
| 파일 전체 코멘트가 렌더링 보기에 안 보임(T16·T17) | PR 데이터에서 `subjectType: FILE` 스레드를 일부러 뺐다. 키가 줄(`R12`)이 아니라 `FILE`이다 | 파일 맨 위(툴바 바로 아래)에 "파일 전체 코멘트" 상자로. 답글·해결·편집·삭제가 되고 요약 수에도 든다 |
| 낡은 스레드가 렌더링 보기에 안 보임 | GitHub 새 "Files changed" 화면도 낡은 스레드는 diff에 두지 않는다(PR 데이터에 키가 없음) | 그대로 둔다(GitHub와 같게) — T17로 고정 |
| 제안 코멘트를 렌더링 보기에서 적용할 수 없음 | 제안 표는 GitHub 모양 그대로 보이지만 "Commit suggestion"은 GitHub 화면의 기능 | 그대로 둔다 — "GitHub에서 보기" 링크로 간다. T18이 제안 표가 보이는지 본다 |
| 내 코멘트를 고치거나 지우려면 원문 보기로 가야 함 | 기능이 없었다(경쟁 분석 제안 4) | 메타 줄에 **편집**·**삭제**. 편집은 마크다운 원문으로 열고, 삭제는 한 번 더 눌러야("정말 삭제", 4초) |
| 올리기 전 모양을 볼 수 없음 | 기능이 없었다 | 새 코멘트·답글·편집 상자에 **쓰기 / 미리보기** 탭 — GitHub가 렌더링한 HTML을 한 번 더 걸러 보여 준다(멘션·이슈 링크도 같게) |

**요청 확인** — 편집·삭제·미리보기 요청은 GitHub "Files changed" 화면이 보내는 요청을 테스트 저장소에서 그대로 받아 적었다(2026-10-09).

| 기능 | 요청 | 확인 |
|---|---|---|
| 편집 | `PUT /<owner>/<repo>/pull/<n>/page_data/update_review_comment?body_version=<버전>` · `{"body","commentId"}` | 200, 새 `bodyHTML` |
| 삭제 | `DELETE /<owner>/<repo>/pull/<n>/page_data/review_comments/<id>` | 204, REST에서 404 |
| 미리보기 | `POST /preview` 여러 부분 폼 `text`·`repository`·`issue` | 200, HTML |

GitHub 화면은 `x-fetch-nonce` 머리글도 보낸다. 확장처럼 보내지 않아도 세 요청 모두 됐다. CSRF 토큰은 쓰지 않는다. 본문 버전(`bodyVersion`)과 고칠 수 있는지(`viewerCanUpdate`·`viewerCanDelete`)는 PR 데이터에 이미 들어 있다. 편집·삭제·미리보기가 실패하면 그 자리에 이유만 보이고 코멘트 기능 전체를 끄지는 않는다. 코멘트 달기는 다른 요청이라 살아 있을 수 있기 때문이다.

**만들며 생긴 회귀와 조치**

| 일 | 원인 | 조치 |
|---|---|---|
| `verify pr` 1차에서 카나리 6/7 — "연결률" 단계가 렌더링 본문을 둘 찾음 | 미리보기 칸에 `markdown-body` 클래스를 붙여, 코멘트 상자가 열리면 `.prose-diff .markdown-body`가 둘이 됐다 | 클래스를 뺐다. 글꼴·목록 모양은 둘러싼 본문에서 물려받는다. 2차 7/7 |

## 5. 검증 등급 — 무엇을 돌리고 얼마나 걸리나

`pnpm verify <등급>` 하나로 돈다. 단계가 실패해도 끝까지 돌고, 결과를 `.scratch/verify/<날짜-시각>-<등급>/report.md`에 아래 모양으로 남긴다. 시간은 1.3.0을 개인 맥북에서 잰 것이다(2026-10-09).

| 등급 | 언제 | 단계 | 테스트 저장소 시나리오 | 걸린 시간 |
|---|---|---|---|---|
| **quick** · 최소 | 개발하면서 수시로 | 타입 → 단위·DOM(284) → 빌드 → 테스트 저장소 맞추기 → `@quick` 시나리오 | T01 렌더링 · T04 기존 스레드 자리 · T05 "+" 줄 · T15 변경 이동(읽기만, Split) | **43초** |
| **pr** · 중간 | PR 병합 전 | quick의 앞 셋 → E2E(12, 데모 PR에 쓰기) → 카나리(7, 실제 GitHub 읽기) → 테스트 저장소 맞추기 → Split 전체 | T01–T24 전부(Split) | **5분 35초** |
| **release** · 전체 | 스토어 검수 요청 전 | pr 전부 → 화면 모양 5가지 → 공개 PR 16개 재탐험 → 성능(확장 끔·켬 2회, md 56·334개 PR) → 스토어 패키지 | T01–T24(Split) + `@layout` 9개 × Unified·공백 숨김·코멘트 접기·좁은 줄 간격 | **15분 29초** |

새 시나리오를 더할 때는 태그로 등급을 고른다. 빠르고 읽기만 하면 `@quick`, 화면 모양에 따라 달라질 수 있으면 `@layout`이고, 나머지는 `pr`부터 돈다.
